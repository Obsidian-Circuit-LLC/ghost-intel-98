# Ghost Intel 98 v3.27.0 — Crash-safety, per-tool scraping cases, OSINT consolidation

**Status:** design / spec (awaiting operator review)
**Target release:** v3.27.0 (single bundled release — "hold for everything", operator 2026-07-02)
**Origin:** GhostExodus dogfooding feedback batch relayed by operator, 2026-07-02.

## Goal

Fix three live-casework-breaking bugs (whole-app crashes, a Tor-resolution hang, an X-credential race) and land five consolidation/UX features (per-tool scraping case stores, OSINT desktop→Toolkit consolidation with an Access-menu flyout, an installer cleanup opt-in, a Searchlight graph reset) in one release, without weakening any stated privacy/security invariant.

## Architecture summary

Each workstream is independently testable and touches a narrow, already-mapped seam. The two structurally significant pieces are W1 (a module-level React error boundary that converts any single-tool crash into a contained dead window — a category fix) and W4 (two new encrypted, per-tool scraping case stores plus a reversible one-time migration of existing SOCMINT/X data out of the investigation cases). Everything else is small-to-medium, localized edits.

## Global Constraints

Copied verbatim from the charter / project invariants — every task's requirements implicitly include these:

- **No telemetry, no phone-home, no analytics beacons.** None added anywhere.
- **No new network egress** beyond what each feature's existing gate already governs. Specifically: host-resolution stays Tor-only (never clearnet); GhostScrape stays inside the X clearnet quarantine (`src/main/x/**` must not import bgconn/Tor/chat-transport/searchlight-tor-socks/socmint-collector; ALLOWED_CROSS_DIR = socmint/store,rank,utils, security/validate).
- **Encrypt at rest.** All case data — including the new scraping stores — persists through secure-fs (`secureReadText`/`secureWriteFile`), never the `readJsonPlain`/`writeJsonPlain` bypass variants.
- **Determinism in correctness-critical paths.** The migration (W4) must be deterministic and idempotent (re-running after a marker is written is a no-op); no `Date.now()`-ordered iteration affecting which store an item lands in.
- **Commits** as persona `onna-bugeisha-dev-team <dev@onna-bugeisha.org>`; NEVER `Co-Authored-By` / `Signed-off-by` / `Claude-Session` trailers in author, committer, or body.
- **Do not touch the pre-existing dirty files**: `pnpm-lock.yaml`, `resources/satellites/active-snapshot.tle`, `native/dcs98-confine/Cargo.lock`.
- **Version** → `3.27.0` in `package.json`; update `README.md` (Status, install line, direct-link + Get-FileHash, test count), release notes, profile README (6 spots per `profile-readme-format-change`).

## W1 — Crash safety: module error boundary + Hosts/News/Camera standalone entries

**Problem.** Opening Host Info or News from the OSINT Toolkit crashes the entire app to a blank teal desktop. Camera-view will crash identically.

**Root cause (confirmed).** `HostInfoModule.tsx:8` (`stream.label`) / `:11`, `NewsViewModule.tsx:12` (`stream.label`, `stream.kind`), and the `CameraView` adapter require a `stream` prop and dereference it on first render. The v3.26.0 Toolkit tagging (`register-builtins.tsx:236-238`, commit `54cce85`) turned all three into `category:'osint'` tiles; the Toolkit launcher (`OSINTToolkitModule.tsx:24`) and the future flyout open them with **no props**, so the adapters (`register-builtins.tsx:167-177`) pass `stream={undefined}` → `TypeError` thrown during React render. `ModuleHost.tsx:25` renders `<C spec={spec}/>` with no error boundary (the only boundary, `geoint/MapErrorBoundary.tsx`, is scoped to the GeoINT map), so an unhandled render throw unmounts the whole React tree → teal screen.

**Design.**
- **(a) Error boundary (category fix).** Wrap the component render in `ModuleHost.tsx` in a React error boundary (mirror `MapErrorBoundary.tsx`) that renders a contained Win98 "This tool failed to load" panel (with the error message + a Close affordance) instead of letting the throw reach root. This makes every future "module throws on mount" a single dead window, not an app crash.
- **(b) Real standalone entries** so the three tools work as tiles (the user wants them in the Toolkit):
  - **Host Info:** when opened with no `stream`, render a small entry form — a host/IP text field + "Resolve" — that constructs the same shape `HostInfoView` expects and runs the (Tor-only, W2-fixed) resolution. When a `stream` *is* passed (EyeSpy/GeoINT flow), behave exactly as today.
  - **News:** when opened with no `stream`, open the live-news viewer against a default feed (the same viewer the GeoINT `LiveNewsPanel` pop-out uses), so it's a usable standalone news reader.
  - **Camera:** when opened with no `stream`, render a "paste stream URL (rtsp/http/hls)" entry (or a hint to launch from EyeSpy/GeoINT). Minimal — just enough that the tile is functional, not a crash.

**Touch points.** `src/renderer/shell/ModuleHost.tsx` (boundary), `src/renderer/modules/hostinfo/HostInfoModule.tsx` + view (entry form), `src/renderer/modules/geoint/NewsViewModule.tsx` (default-feed standalone), `src/renderer/modules/*/CameraView*` (URL entry). Keep the `category:'osint'` tags (the tools stay in the Toolkit) now that they degrade gracefully. Update `test/osint-toolkit-module-registered.test.ts` reachability audit accordingly (all 10 remain reachable, now safely).

**Tests.** Boundary: a module whose render throws produces the fallback panel, not an unmount (render-throw component under `ModuleHost`). Each of Host Info / News / Camera: mounting with `props: undefined` renders the entry form, not a throw; mounting with a valid `stream` renders the normal view.

**Risk.** Low. The boundary is additive; the entry forms guard an existing crash.

## W2 — CCTV host-resolution: kill the Tor hang, keep Tor-only, add explicit toggle

**Problem.** The Host-resolution panel hangs on "resolving via Tor…" even with "Route CCTV streams through Tor" unchecked, and eventually shows "Couldn't fully resolve via Tor (…)".

**Root cause (confirmed).** `geoint.cctvOverTor` (`types.ts:431`, default `:634`; checkbox `SettingsModule.tsx:695-700`) gates **only** the media-stream proxy (read in `eyespy/Viewer.tsx`; no `src/main` reader). Host resolution is a **separate, hardcoded Tor-only recon path** — IPC `register.ts:1438-1442` ("Tor-only DNS/RDAP recon", reads no setting) → `hostinfo/index.ts:35-45` `torFetchJson` → `resolve.ts:31/42/47` (DoH A / PTR / RDAP), error `rdap-failed` at `:49`. The hang is the bgconn footgun: `ensurePluginTor()` (`tor-egress.ts:190-210`) awaits `tor.start()` which resolves only on "Bootstrapped 100%" (`:205`) with **no `isBootstrapped()` fast-fail / `TOR_UNAVAILABLE` guard**. `HostInfoView.tsx:9` auto-fires the lookup on open, so it blocks indefinitely when Tor is slow/offline.

**Design (keep Tor-only — clearnet resolution would leak the operator's real IP to Cloudflare/rdap.org, weakening an IP-exposure invariant).**
- **Fix A (the real bug):** in `torFetchJson` (`hostinfo/index.ts:35`), fast-fail when the plugin-egress Tor isn't bootstrapped: if `getPluginTor()?.isBootstrapped()` is false, kick `ensurePluginTor()` off in the background (fire-and-forget) and immediately throw a typed `tor-not-ready` error (or race `ensurePluginTor()` against a bounded timeout). `resolveHost` returns a partial `HostInfo` fast instead of hanging.
- **Fix B (UX contract):** add an explicit setting `geoint.cctvResolveHosts` (default **on**). When **off**, host resolution is disabled entirely (the panel shows "Host resolution is turned off in Settings → GeoINT" and does not fire a Tor lookup). When **on** but Tor isn't ready, `HostInfoView` shows "Host resolution needs Tor (bootstrapping / unavailable)" rather than an infinite spinner. Fix the copy so it reads as a distinct Tor-only recon step, independent of the stream checkbox.

**Touch points.** `src/shared/types.ts` (`geoint.cctvResolveHosts` decl + default, plus settings-merge list per `settings-merge-upgrade-dataloss`), `src/renderer/modules/settings/SettingsModule.tsx` (new checkbox under GeoINT, corrected copy for both), `src/main/services/hostinfo/index.ts` (`isBootstrapped()` fast-fail), `src/renderer/modules/**/HostInfoView.tsx` (off-state + not-ready state, gate the auto-run), `src/main/ipc/register.ts:1438` (honor the resolve setting; return fast).

**Tests.** `torFetchJson` throws `tor-not-ready` synchronously (fast) when `isBootstrapped()` is false (mock plugin-Tor), and does not await `start()`. Resolution disabled when `geoint.cctvResolveHosts=false`. Settings upgrader carries the new field (merge-guard test).

**Risk.** Medium — Tor plumbing. Must not weaken the Tor-only invariant; add a test asserting resolution never issues a clearnet fetch.

## W3 — GhostScrape: per-job session isolation (fix the credential race)

**Problem.** The X/Twitter scraper throws errors / cross-contaminates credentials.

**Root cause (confirmed).** `ghostscrape/ipc.ts:116-151` `start()` is fire-and-forget with **no mutex/queue** — concurrency is permitted. Every job opens a window on the **shared** `persist:ghostscrape` partition (`browser.ts:29,52-73`) and writes domain-level `.x.com` cookies (`cookies.ts:42-61`), so two jobs for different `accountId`s clobber each other's auth mid-flight. Softer surfaces: a broken CDP capture silently returns 0 items (`capture.ts:64-94`, `browser.ts:82-111`) surfaced as a "successful" empty job; `sendDone` drops events if the window is stale (`ipc.ts:101-113`); `toConfig` raw throws (`ipc.ts:65,68`) bypass `safeJobErrorMessage`.

**Design.**
- **Per-job ephemeral partition.** In `browser.ts:52`, open each job's window on a **non-persistent** unique partition `ghostscrape-${jobId}` instead of `persist:ghostscrape`. Concurrent jobs can no longer share/overwrite a cookie jar, and no persistent cookie residue remains on disk. (Belt-and-suspenders: optionally serialize jobs with a single-flight guard in `ipc.ts:116`, but isolation alone fixes the race.)
- **Honest empty result.** When a job completes with `captured: 0` because capture never attached (vs. genuinely no tweets), surface a distinct "couldn't capture timeline (session may be invalid — re-add cookies in X Intel)" message rather than a silent success.
- **Quarantine preserved.** All changes stay within `src/main/x/**`; no forbidden cross-imports; deps stay injected.

**Touch points.** `src/main/x/ghostscrape/browser.ts:52` (partition), `src/main/x/ghostscrape/ipc.ts` (empty-result surfacing; keep `safeJobErrorMessage` mapping), `src/main/x/ghostscrape/errors.ts` (new typed message if needed). Verify X Intel collector (`x/ipc.ts`) for the same shared-partition pattern and apply the same isolation if present.

**Tests.** Two concurrent jobs get distinct partition strings (unit on the partition-name derivation). A `captured:0` with no capture attach maps to the distinct message, not success. Quarantine sentinel test still green.

**Risk.** Low-medium. Ephemeral partitions mean cookies are set per job every run (already the case) — confirm no assumption that the jar persists between jobs (it shouldn't).

## W4 — Per-tool scraping case stores + migration + import-to-case

**Problem.** SOCMINT lists the investigation cases (`SocmintModule.tsx:698` calls `cases.list()`) and SOCMINT/X items persist **inside** main case dirs. The user wants scraping/monitoring cases fully separate, with their own left-hand Cases sidebar, and results optionally importable into a main case.

**Current state (confirmed).** Main store `caseStore` (`storage/json-fs.ts:211+`) → `dataRoot()/cases/<id>/case.json` (encrypted). SOCMINT items/jobs → `<caseDir>/socmint-items.json` / `socmint-jobs.json` (`socmint/store.ts:136-137`, injectable at `:128-138`). X Intel is **not** a separate store — `x/ipc.ts:313-317` reads the SOCMINT store filtered `platform:'x'`. GhostScrape saves via `notes.write(caseId, …)` into main case notes (`GhostScrapeModule.tsx:172-177`).

**Design (two stores: `socmint` + `x`; X Intel and GhostScrape share `x`).**
- **Generic store factory** `src/main/storage/scraping-cases.ts` — `makeScrapingCaseStore(namespace)` returning `{ list, create, read, rename, delete }`, mirroring `caseStore`, persisting through secure-fs. Instantiated for `'socmint'` and `'x'`.
- **Paths** (`storage/paths.ts`): `scrapingCasesDir(ns)` → `dataRoot()/scraping-cases/<ns>/`, `scrapingCaseDir(ns,id)`, `scrapingCaseFile(ns,id)`, and per-case item/note paths under it.
- **Types** (`shared/types.ts`): a slim `ScrapingCase { id; name; createdAt; updatedAt; note? }`.
- **IPC** (`shared/ipc-contracts.ts` + `ipc/register.ts` ~`:494` + preload): one namespace `scrapingCases.*` taking a validated `store: 'socmint'|'x'` discriminator (allowlist-checked main-side — reject any other value) → `{list,create,rename,delete,importToCase}`. Exposed as `window.api.scrapingCases`.
- **Repoint item persistence** to the new dirs via the existing injectable resolver: SOCMINT store `socmint/store.ts:128-138` resolves against `scrapingCaseDir('socmint', id)`; X items (`x/ipc.ts` upsert/list) against `scrapingCaseDir('x', id)`; GhostScrape "save to case" writes an artifact under `scrapingCaseDir('x', id)` (new `scrapingCases.saveArtifact` or note path) instead of main case notes.
- **Left-hand Cases sidebar** (the image-8 concept) in `SocmintModule` (store `'socmint'`) and `XCollectorModule` + `GhostScrapeModule` (store `'x'`): "Add Case" (name prompt), list, Open, Delete — reading the respective scraping store, **not** `cases.list()`. Replaces `SocmintModule.tsx:698` / `GhostScrapeModule.tsx:154` pickers and the X free-text case-id field.
- **Import into a main case:** `scrapingCases.importToCase(store, scrapingCaseId, mainCaseId)` reads the scraping case's items/artifacts and re-writes them into the main case via the existing `caseStore`/`noteStore`/SOCMINT `upsertItems` writers. A renderer action ("Import to case…") in each sidebar.

**Migration (the highest-risk piece — own tests, reversible).**
- One-time, deterministic, idempotent migrator (guarded by a marker file, e.g. `dataRoot()/scraping-cases/.migrated-v3.27.0`). On first run: scan every main case dir for `socmint-items.json`/`socmint-jobs.json`; **split X-platform items** (`platform:'x'`) into the `x` store and the rest into the `socmint` store, creating a scraping case per source main case (named after it). **Back up** the original files to `dataRoot()/scraping-cases/backup-pre-v3.27.0/<caseId>/` before removing them from the main case dir. Write the marker. Re-running with the marker present is a no-op.
- GhostScrape artifacts previously saved as main-case notes: leave in place (they're notes, not structured items) — migration targets the structured SOCMINT/X item/job files only. Document this.

**Touch points.** `storage/paths.ts`, new `storage/scraping-cases.ts`, new `storage/scraping-migration.ts`, `socmint/store.ts:128-138`, `x/ipc.ts` (upsert/list dirs), `shared/ipc-contracts.ts`, `shared/types.ts`, `ipc/register.ts`, preload, `SocmintModule.tsx`, `XCollectorModule.tsx`, `GhostScrapeModule.tsx`, `socmint/case-options.ts`. Core `caseStore` unchanged.

**Tests.** Store factory round-trips through mock secure-fs (create/list/rename/delete) for both namespaces. Namespace allowlist rejects an unknown `store` value. Migration: given fixtures with mixed SOCMINT + X items in main cases, produces the correct split into the two stores, writes the backup, is idempotent (second run no-ops), and is reversible from the backup. `importToCase` writes items into the main case. Determinism: identical fixtures → identical store contents.

**Risk.** High (data movement over live casework). Mitigated by: copy-then-verify-then-remove ordering, retained backup, marker-guarded idempotency, dedicated migration tests. This workstream ships last among the W1–W7 features and gets the most review scrutiny.

## W5 — OSINT consolidation: desktop declutter, Access-menu flyout, compact Toolkit

**Problem.** OSINT tools clutter the desktop; the Access-menu "OSINT Toolkit" should be a one-hop submenu; the Toolkit window should be compact.

**Design.**

- **(b) Access flyout:** in `AccessMenu.tsx` — add `OSINT_TARGETS` (the 10 osint keys, or derive from `listModules().filter(m=>m.category==='osint')`); extend the flat-filter (`:37-39`) to also exclude `OSINT_TARGETS` (so eyespy/geoint/searchlight/socmint stop appearing as flat rows); replace the single OSINT Toolkit entry (`:122-134`) with a Games-cloned flyout (`osintOpen` state, hover wrapper, `left:100%` panel) populated from `buildOsintDirectory(listModules())` — group headings + one row per tool, each calling `openModule(tool.key, tool.title)`. - **(c) Compact window:** lower `defaultWidth/Height` at `register-builtins.tsx:244` to a compact folder size (~360×460). Keep the Toolkit window (opened from the desktop icon and optionally a flyout header) as well as the flyout — both surfaces, one grouping source.

**Touch points.** `src/renderer/shell/Desktop.tsx:22-24`, `src/renderer/shell/AccessMenu.tsx` (flyout + filter), `src/renderer/modules/register-builtins.tsx:244` (size). Reuse `buildOsintDirectory`.

**Tests.** `desktopShortcutDefaults` no longer contains `searchlight`/`socmint`. Access flat-items exclude OSINT targets. Flyout grouping equals `buildOsintDirectory` order (reuse the existing directory test). ADHD-UX: flyout is one hop (no nested sub-submenus).

## W6 — Installer: opt-in "remove previous instance data" checkbox (non-mandatory)

**Problem.** No way to clean a prior install's data/config; the uninstaller leaves `%APPDATA%` behind.

**Current state (confirmed).** electron-builder config inline in `package.json build` (`:94-209`); `win`→nsis at `:178-200`; `oneClick:false` (`:191`), `perMachine:false` (`:192`) → per-user, no elevation. **No** custom `.nsh`, no `include`, `deleteAppDataOnUninstall` unset. `directories.buildResources:"resources"` (`:99`). App data at `%APPDATA%\Ghost Intel 98` (inner `GhostAccess98/` per `paths.ts:11-13`); prior-name dirs `Dead Cyber Society 98`, `Ghost Access 98` (`migrate-userdata.ts:25`). App writes no registry keys of its own.

**Design.** Add `"include": "installer.nsh"` to the nsis block (`package.json:190-200`). New `resources/installer.nsh`:
- `!macro customPageAfterChangeDir` — nsDialogs page with a checkbox "Remove data and settings from a previous installation" created **unchecked** by default; `${NSD_OnClick}` stores `1/0` into `Var /GLOBAL CleanPrevData`.
- `!macro customInstall` — `${If} $CleanPrevData == 1`: existence-guarded `RMDir /r "$APPDATA\Ghost Intel 98"` (+ optionally `$APPDATA\Dead Cyber Society 98`, `$APPDATA\Ghost Access 98`). Never touch `$INSTDIR` (electron-builder manages it on upgrade). `secrets.enc` is DPAPI-scoped, so deleting the file suffices.

Explicitly **non-mandatory**: default unchecked; install proceeds normally when unchecked.

**Touch points.** `package.json` nsis block (`include`), new `resources/installer.nsh`.

**Tests.** No unit test harness for NSIS; verified at package/QA time (W8) — build the installer, confirm the page appears and the checkbox defaults unchecked, and (in the VM/human smoke) that checking it removes prior `%APPDATA%` data while unchecked leaves it. Note this limitation honestly in the plan.

**Risk.** Medium — destructive filesystem op in the installer. Mitigations: default off, existence guards, scoped to `%APPDATA%` app dirs only, never `$INSTDIR`, human-verified in QA.

## W7 — Searchlight: reset the relationship-tree graph + re-import

**Problem.** No way to wipe the whole relationship graph; only per-node/edge deletes exist.

**Current state (confirmed).** Graph view `searchlight/panels/GraphView.tsx` (rendered `SearchlightModule.tsx:84-85`); data is **store-backed per-case** on `SearchlightCase.graphNodes/graphEdges` (`shared/searchlight/types.ts:97-98`), mutated via `store.ts:264-313` through `mutateCaseAndSave` → debounced `saveCase` → `main/searchlight/store.ts:29-31` (`secureWriteFile`, one file per case). No whole-graph clear exists. Re-import already exists and is idempotent/additive: `importResultsToGraph` (`GraphView.tsx:345-413`), driven by the Import panel (`:521-634`).

**Design.**
- New store action `clearGraph(caseId)` (`store.ts`, near `:305-313`): `mutateCaseAndSave` sets `graphNodes:[]`, `graphEdges:[]`, `updatedAt:Date.now()` — persisted by the existing debounced save; no main-process change.
- New confirm-gated "Clear Graph" toolbar button (`GraphView.tsx` ~`:510`, `sl-sweep-btn-danger` style already at `:491`). On confirm: `clearGraph(activeCaseId)` then reset local view state (`setSelected(null)`, `setConnecting(null)`, `setEditingNote(null)`, `setShowAddMenu(false)`) so no stale node-id lingers. Optionally a "clear then re-import current case" convenience (`clearGraph` → `importResultsToGraph(activeCaseId, new Set(), true)`).
- **Per-case scoped** — key everything off `activeCaseId` (do not clear globally). Per `searchlight-panel-unmount-state`: GraphView derives nodes/edges fresh from `activeCase` and holds no cross-case pointer, so the stale-pointer/blank-panel bug does not apply; keep it that way and only reset local `useState`.

**Touch points.** `src/renderer/modules/searchlight/store.ts` (`clearGraph`), `src/renderer/modules/searchlight/panels/GraphView.tsx` (button + confirm + local reset). No main-process or types change.

**Tests.** `clearGraph(caseId)` empties that case's `graphNodes`/`graphEdges` and touches no other case; the debounced save writes the emptied case. Re-import after clear rebuilds from sweep results (existing `importResultsToGraph` path).

**Risk.** Low.

## Build sequencing

Order: **W1 (crash safety) → W3 (X race) → W2 (Tor hang) → W7 (graph reset) → W5 (consolidation) → W6 (installer) → W4 (scraping cases + migration, last & most-reviewed)**.
